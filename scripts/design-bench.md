# design-bench — frontend-design benchmark

A thin wrapper around `scripts/orchestration-bench.ts` that runs the same
frozen design prompt against several models in isolated blind workspaces,
validates visual proofs, supports blind human rubric grading, and produces a
comparison report that separates **design score** from **efficiency metrics**.

Definitions live in `scripts/bench-defs/design/`, prompts in
`scripts/bench-prompts/design/`. The session runner, telemetry, and
control-drift primitives are reused from orchestration-bench — this wrapper
adds only design-layer concerns.

## Run-root layout

```
<runRoot>/
  manifest.json    # frozen benchmark config, fingerprints, candidate statuses
  map.json         # candidate label → model mapping (NEVER open while grading)
  candidates/<label>/workspace/   # per-candidate fixture copy (session cwd)
  records/<label>.json           # per-candidate telemetry + status (contains model)
  scores/<label>.json            # human rubric scores (blind)
  report.md / report.json        # generated by `report`
```

## Exact commands

### 1. Initialize a benchmark run (freezes definition + model list)

```bash
bun scripts/design-bench.ts init scripts/bench-defs/design/dashboard-home-v1.json \
  --models "openrouter/z-ai/glm-5.3-flash,anthropic/claude-opus-4-8" \
  --repeat 2 --seed 42 --thinking high \
  --timeout-ms 1800000 \
  --out /home/chris/bench-runs/dashboard-home-v1
```

`--seed` may be a number or any string (string is hashed). Same seed ⇒ same
blind mapping. Model selectors are `provider/modelId` (OMP resolution rules).

### 2. Run one model (by blind label — the mapping is in map.json)

```bash
bun scripts/design-bench.ts run <runRoot> --only candidate-003
```

### 3. Run all remaining candidates

```bash
bun scripts/design-bench.ts run <runRoot>
```

Failed/timeout candidates can be retried by re-running; each retry reseeds a
fresh workspace. `--only <label>` runs a single candidate.

### 4. Verify artifacts from disk without re-running

```bash
bun scripts/design-bench.ts validate <runRoot>
```

Exit 1 if any candidate is not review-ready. A run that exited 0 without
producing the required proofs is marked `invalid` — never a success.

### 5. Blind review index (no model identity)

```bash
bun scripts/design-bench.ts candidates <runRoot>          # human-readable
bun scripts/design-bench.ts candidates <runRoot> --json   # machine-readable
```

Shows each candidate's status, review-readiness, elapsed time, and proof
paths. Do **not** open `map.json` or `records/*.json` while grading — they
contain model identity.

### 6. Record a rubric score (100-point rubric, deduction flags)

Write a score JSON (keys = rubric criterion ids, values within `[0, weight]`):

```json
{
  "scores": {
    "visual-quality": 18, "hierarchy-glanceability": 14, "genuine-redesign": 10,
    "mobile-density": 7, "data-priority-correctness": 8, "concept-strength": 6,
    "desktop-adaptation": 3, "constraint-compliance": 4
  },
  "deductions": ["fabricated-metrics"],
  "note": "Strong rows but invented a battery meter.",
  "reviewer": "chris"
}
```

```bash
bun scripts/design-bench.ts score <runRoot> candidate-001 --file /tmp/score-001.json
```

Scores outside the legal range or with unknown deduction ids are rejected.

### 7. Blind report (no model identity)

```bash
bun scripts/design-bench.ts report <runRoot>
```

Writes `report.md` + `report.json`: fingerprint, control drift, per-candidate
status/scores/proofs. Ungraded candidates are shown as **ungraded**, not zero.

### 8. Reveal the mapping

```bash
bun scripts/design-bench.ts reveal <runRoot>
```

### 9. Final comparison report (after grading)

```bash
bun scripts/design-bench.ts report <runRoot> --reveal
```

Adds candidate→model mapping and per-model aggregation (mean/median/best/
worst design score by criterion, valid-run counts, failure counts) plus
efficiency metrics (tokens, wall clock, model time) in a **separate section**.

## Invariants

- All candidates get the same prompt bytes and fixture bytes; drift on any
  non-model control (prompt, fixture, benchmark fingerprint, harness, git
  head, thinking level, **tool/capability surface**) is reported in every
  report. The capability surface is frozen in the definition's `capabilities`
  object (`configFiles` are passed to every OMP session and must exist at
  init), hashed into the benchmark fingerprint, recorded per candidate, and
  drift-checked. Per-candidate workspace paths are intentionally excluded —
  isolation mandates them; content equality is enforced via the fixture
  fingerprint instead.
- Blind labels are shuffled by seed so label order does not reveal model
  order.
- `pending → success | partial | failed | timeout | invalid` — only `success`
  with verified proofs is review-ready; only valid graded runs enter model
  aggregates.
